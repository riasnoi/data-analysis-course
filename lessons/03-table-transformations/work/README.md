## 01. Входы, строка и ключ

В таблице `decisions` (`6830` строк) одна строка означает одну ипотечную заявку с уникальным номером `source_row`, в справочнике `organizations` (`470` строк) — одну организацию в конкретном отчётном году по ключу `(lei, activity_year)`, а в сводке `long` (`500` строк) — агрегированное количество заявок `n` для сочетания `(lei, activity_year, action_taken)`[span_4](start_span)[span_4](end_span)[span_5](start_span)[span_5](end_span). Сумма счётчиков `n` в `long` равна `6830`, что полностью совпадает с числом строк в `decisions`[span_6](start_span)[span_6](end_span).

## A. Разворот сводки

Таблица `wide_task` имеет размер `(314, 3)` с многоуровневым индексом `['lei', 'activity_year']` и столбцами исходов `1`, `2`, `3`[span_7](start_span)[span_7](end_span). Число пропусков (`NaN`) по столбцам составило: исход `1` — `20`, исход `2` — `252`, исход `3` — `170` (всего `442` пустые ячейки)[span_8](start_span)[span_8](end_span). Пустая ячейка в `wide_task` означает, что у данной организации в указанном году не зафиксировано ни одной заявки с соответствующим кодом исхода. Для корректной работы `pivot` требуется уникальность сочетания `index + columns` (`lei, activity_year, action_taken`), иначе метод выбросит ошибку из-за неоднозначности при размещении нескольких значений в одну ячейку.

## B. Обратное преобразование

После обратного разворота `wide` через `melt` получено `942` всех возможных сочетаний (`314` организаций × `3` исхода), из которых после фильтрации `n > 0` осталось `500` наблюдаемых сочетаний с суммой `n = 6830`, полностью совпавших с `long` по `assert_frame_equal`[span_9](start_span)[span_9](end_span). Из итоговой таблицы исключены `442` строки с `n == 0`, которые были искусственно материализованы при развороте в широкую форму для заполнения отсутствующих исходов[span_10](start_span)[span_10](end_span).

## C. Сохранность исходных значений

Проверка `assert_frame_equal` по исходным семи столбцам `decisions` и `enriched` после сортировки по `source_row` подтвердила полную сохранность данных, а тест с изменением одного непустого значения `loan_amount` в отдельной копии корректно вызвал `AssertionError`[span_11](start_span)[span_11](end_span). Проверки только длины таблицы (`len(enriched) == 6830`) недостаточно, поскольку она не защищает от искажения значений в столбцах, перепутывания строк местами или замены исходных полей при слиянии[span_12](start_span)[span_12](end_span).

## D. Покрытие неполного справочника

При использовании `partial_lookup` (без первой организации) в `left_partial` выявлено `25` несовпавших строк (`left_only`), которые полностью совпали с 25 номерами `source_row`, потерянными при `inner`-соединении (`6830 - 6805 = 25`), и сохранены в `results/unmatched.csv` вместе с аудитом в `results/join_audit.json`[span_13](start_span)[span_13](end_span)[span_14](start_span)[span_14](end_span). При подключении `replayed_lookup` с дублем первой организации без `validate` размер результата вырос с `6830` до `6855` строк (`wrong_join`), так как каждая из 25 заявок этой организации размножилась в декартово произведение с двумя строками справочника[span_15](start_span)[span_15](end_span)[span_16](start_span)[span_16](end_span). Порядок исправления такого сбоя: остановить слияние контрактом `validate="many_to_one"`, найти дублирующиеся ключи справа через `duplicated(subset=org_keys)`, очистить или агрегировать справочник до уникальности по ключу и повторить `merge`[span_17](start_span)[span_17](end_span).

## E. Передача профиля

В рамках работы решался вопрос оценки уровня одобрения ипотечных заявок по кредитным организациям за отчётный год, где единицей наблюдения в `named_profile` (`314` строк, сохранён в `results/organization_profile.csv` и проверен повторным чтением с `lei` типа `string`) выступает пара `(lei, activity_year)`[span_18](start_span)[span_18](end_span). Данные получены из таблицы заявок `decisions` и обогащены названиями из полного справочника `organizations` через контрактное соединение `left JOIN` с проверкой `validate="one_to_one"`[span_19](start_span)[span_19](end_span). Целостность расчётов подтверждена равенством сумм `n_decisions == 6830` и `n_approved == 6139`, где доля одобрений определена как `approval_rate = n_approved / n_decisions` (отношение заявок с исходами `1` и `2` ко всем рассмотренным заявкам организации)[span_20](start_span)[span_20](end_span). Отношение общих счётчиков по всей выборке составило `0.8988` (`6139 / 6830`, или `89.88%`), тогда как простое среднее процентов по организациям равно `0.8578` (`85.78%`), поскольку простое среднее даёт одинаковый вес мелким и крупным банкам независимо от числа заявок[span_21](start_span)[span_21](end_span). Основным ограничением сравнения является высокая статистическая неустойчивость `approval_rate` у организаций с малым количеством заявок.
