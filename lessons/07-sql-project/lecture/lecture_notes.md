# Лекция 7 SQL и проверка расчётов проекта

2026-12-05. 90 минут.

Сначала изучите эту тему на лекции. На практике в этот день обсуждается предыдущая тема.

## 1 Те же данные, другой способ запроса

Мы уже фильтровали, группировали и соединяли таблицы в pandas. SQL позволяет описать такие действия запросом к базе данных. Начнём с тех же decisions и organizations, чтобы новая запись команд не смешивалась с незнакомой предметной областью.

Для занятия создаём локальную SQLite-базу в памяти и загружаем сохранённые CSV. Нового внешнего сервиса не требуется. Таблица decisions содержит одну опубликованную запись на source_row, справочник — название организации по lei и году. В Python функция query передаёт текст SQL в SQLite и возвращает результат как DataFrame. Сам язык SQL задаёт, какие данные нужны; движок выбирает способ выполнения. Посмотрим первые строки и свяжем имена полей с предыдущими занятиями.

## 2 Ключи связывают таблицы

Реляционная таблица хранит строки с одинаковым набором столбцов. Чтобы различать записи, нужен ключ. В нашем снимке source_row уникален, но этот технический номер не является глобальным идентификатором человека или заявки во всех источниках.

В organizations уникальна пара lei и activity_year. Повтор lei в разных годах допустим, поэтому соединение только по коду в многолетнем наборе может размножить строки. Первичный ключ задаёт уникальность и известность идентификатора в схеме базы. Внешний ключ описывает ссылку на другую таблицу. При загрузке CSV через to_sql ограничения автоматически не появляются: их нужно создавать отдельно или проверять запросами. Сейчас проверим реальные ключи запросом, а затем объясним, какое нарушение вернуло бы строки.

## 3 SELECT и AS

SELECT перечисляет поля или выражения, которые хотим увидеть. FROM называет источник строк. Можно выбрать source_row и loan_amount, а рядом вычислить loan_amount/1000.0 и назвать результат loan_kusd через AS.

Это имя относится к столбцу результата; исходная таблица не меняется. Десятичная точка в делителе подчёркивает вещественное деление. В SQL поведение деления зависит от типов и движка, поэтому его нужно проверять. LIMIT ограничивает количество возвращённых строк для просмотра. Без ORDER BY порядок не гарантирован: первые пять строк результата нельзя интерпретировать как пять самых больших или случайную выборку. Для определённого порядка зададим сортировку отдельно.

## 4 WHERE: условие для строки

WHERE оставляет строки, у которых условие выполнено. Например, action_taken=3 выбирает отказы, а loan_amount>1000000 добавляет ограничение по сумме. В SQL логические AND и OR относятся к условиям строк запроса. Это другой язык, чем Python-операторы над pandas Series.

Скобки помогают явно задать, какие условия объединяются. Перед выполнением прочитайте отбор словами: отказы с суммой больше миллиона. Затем сравните размер результата с той же маской pandas. Такой контроль полезен при переносе анализа между инструментами. Строковые значения в SQL записываются в одинарных кавычках; значения из пользовательского ввода будем передавать параметрами, чтобы не собирать запрос конкатенацией.

## 5 NULL: неизвестное значение

В базе неизвестное значение обозначается NULL. Проверка income=NULL не работает как проверка равенства обычному числу: сравнение с неизвестным даёт неизвестный логический результат. WHERE оставляет только условия True. Поэтому пропуски ищут через IS NULL и IS NOT NULL.

COUNT(*) считает все строки, COUNT(income) — строки с известным доходом. Разность даёт число пропусков. В нашем снимке это 342. Сумма и среднее обычно пропускают NULL; если требуется другое поведение, его нужно определить явно. COALESCE может заменить NULL заданным значением, но подставлять ноль в неизвестный доход без смыслового основания нельзя. Сначала покажем оба счётчика и свяжем их со знакомыми len и count pandas.

## 6 ORDER BY и LIMIT

Чтобы получить крупнейшие суммы, отсортируем loan_amount по убыванию через DESC и только потом ограничим результат. При одинаковых суммах добавим source_row как второе поле порядка. Тогда повторный запрос вернёт однозначно выбранные строки.

LIMIT без сортировки удобен для короткого просмотра, но не задаёт статистическую выборку и не гарантирует устойчивый порядок. Сортировка по одному неуникальному показателю тоже оставляет неопределённость внутри совпадений. На больших базах порядок результата и эффективность запроса — отдельные вопросы; сейчас наша задача получить проверяемую таблицу. Сравним пять верхних сумм с pandas, используя те же направления сортировки по обоим полям.

## 7 GROUP BY: одна строка на группу

GROUP BY объединяет строки с одинаковыми значениями выбранных полей. Посчитаем число записей и среднюю сумму по action_taken. В результате три строки, каждая относится к одному исходу.

SELECT в таком запросе должен выражать смысл группы: её ключ и агрегаты. SQLite допускает некоторые запросы с неагрегированными полями вне GROUP BY, но их результат может быть произвольным для группы. Поэтому не выбираем source_row рядом со средним исхода без отдельного правила. Размер результата группировки и число исходных записей различаются. Проверим, что сумма групповых n равна 6830, затем сравним средние с pandas. Так мы переносим определение показателя, а не только синтаксис.

## 8 HAVING: условие для готовой группы

Допустим, нужен профиль организаций хотя бы с двадцатью решениями. Сначала GROUP BY lei, activity_year создаёт группы и COUNT(*) считает их размер. Затем HAVING COUNT(*)>=20 оставляет подходящие группы.

WHERE действует раньше: если написать там action_taken=3, размер станет количеством только отказов. Это уже другой показатель и другой порог. Прочитайте оба возможных вопроса: организации с двадцатью всеми решениями или организации с двадцатью отказами. Названия полей и порядок операций должны удерживать различие. Запрос выводит группы, а не исходные записи; проверка source_row здесь не относится к результату. Сохраним n и ключ, чтобы следующий этап мог явно использовать состав профиля.

## 9 CASE: условное вычисление

CASE WHEN позволяет вычислить значение по условию. Создадим индикатор отказа прямо в запросе: если action_taken=3, результат 1.0, иначе 0.0. Среднее такого индикатора равно числу отказов, делённому на количество строк.

По каждой организации получим n_decisions, n_denied и denial_rate. Числитель и знаменатель относятся к одной группе. Если нужен другой набор исходов, сначала фиксируем его через WHERE и описываем в определении. Нельзя незаметно исключить часть записей только из знаменателя. CASE полезен для условных агрегатов и в SQL-таблицах признаков, но каждое новое вычисляемое поле нужно назвать так, чтобы его формула читалась без догадок.

## 10 JOIN: поиск совпадения по ключу

JOIN сопоставляет строки двух таблиц по условию ON. Назовём decisions коротким псевдонимом d, organizations — o. Условие d.lei=o.lei AND d.activity_year=o.activity_year повторяет наш составной ключ из pandas merge.

При уникальном правом ключе каждая левая запись найдёт не более одной строки справочника. Если справа есть повтор, SQL создаст несколько совпадений и увеличит результат; автоматического validate="many_to_one" здесь нет. Поэтому проверку справочника выполняем отдельно. Выберем исходный source_row и добавленное название, затем проверим число строк. Не используем SELECT * без необходимости: одноимённые ключи и лишние поля усложнят чтение результата.

## 11 LEFT JOIN и фильтр после него

LEFT JOIN сохраняет все левые строки. Если справочник не содержит соответствия, добавленные поля будут NULL. INNER JOIN оставляет только совпавшие пары. Это уже знакомое различие, теперь прочитаем его в SQL.

Особенно внимательно смотрим на WHERE после LEFT JOIN. Условие по правому полю, например o.organization_name IS NOT NULL, удалит несовпавшие строки. Так запрос, внешне содержащий LEFT JOIN, перестанет сохранять весь левый состав. Для отчёта покрытия посчитаем несовпавшие отдельно. Если специально используем неполную копию справочника, подпишем её как учебный вариант. Не будем объявлять каждую такую строку ошибкой ипотеки: отсутствие справочного имени и исход заявки относятся к разным полям.

## 12 Параметры вместо подстановки текста

В практическом анализе порог или код исхода может приходить из переменной. Не будем вставлять его в строку SQL через f-string. SQLite поддерживает параметры: в тексте ставим вопросительный знак, а значения передаём отдельным кортежем.

Так значение обрабатывается как данные, а не как часть команды. Это защищает от ошибок кавычек и нежелательного изменения запроса. Параметрами подставляют значения; имя таблицы или столбца так не выбирается. Для выбора имён нужен отдельно ограниченный набор допустимых вариантов. В нашем примере передадим код исхода и порог суммы, затем сравним результат с уже проверенным фильтром. Сам текст запроса останется неизменным при изменении параметров.

## 13 Сверяем SQL и pandas

Проверим профиль организаций независимо через pandas. Сгруппируем те же записи по lei и году, посчитаем n_decisions и n_denied. Отсортируем оба результата по ключам и сравним счётчики.

SQL и pandas могут возвращать разные технические типы, особенно для NULL и текстовых кодов. Поэтому сначала проверим содержательные поля и типы, затем при необходимости приведём представление к явному общему формату. Не будем скрывать несовпадения округлением до сравнения. Успешная независимая сверка говорит, что два пути реализовали выбранное определение. Она не доказывает правильность вопроса сама по себе: определение доли и состав данных всё равно должны быть записаны словами.

Для каждого запроса сначала назовите смысл одной строки результата. Если это профиль организации, ключ — организация и год; если обогащённые решения, должны сохраняться исходные source_row. Рядом с SQL сохраняйте проверку и описание показателя. Передача включает текст запросов и полученные CSV.
